# Professional Practice course modernisation

Run this workflow in Codex Cloud with GPT-6.2 Sol. Use the Professional Practice repository on current `origin/main`. Read `AGENTS.md`, the [working backlog](../docs/course-modernisation-backlog.md), the [media plan](../docs/media-and-diagram-plan.md), the [e-learning roadmap](../docs/e-learning-roadmap.md), and the [explainer build instructions](../explainers/README.md). Check Git status before editing. Use the repository as the durable record across isolated runs.

## Audit and pick work

1. Inventory all eight parts every run. Cover the authored slide text, active narratives, textbook, quizzes, practice artefacts, linked resources, existing explainers, labs and course notes. Compare the inventory with the last reviewed revision. Inspect new and changed content, overdue volatile claims, and the next unreviewed topics. Record which topics and surfaces were inspected and what remains. Carry the audit forward until every topic has been assessed for both freshness and production opportunities, then revisit as sources and examples change.
2. Check potentially dated statements against current primary sources, especially product behaviour, certification versions, metrics, legal requirements, policies and figures. Record the claim, source path and location, direct reference, checked date and proposed correction. Distinguish historical examples that still teach the point from current instructions that need revision. Check parallel slide, narrative, assessment and textbook wording before making a correction. Update or invalidate stale narration audio using the existing provenance workflow.
3. Add opportunities when movement, time, space or a learner decision can teach something more clearly. Record the learning objective, the source lesson, the chosen format, what the learner will see or do, and any content, platform or review dependency. Reuse existing material and check whether an equivalent activity is already in the course or the SCORM package. Keep cultural review requirements and the distribution boundaries of paid content.
4. Each run should deliver a small verified improvement from the backlog. Prioritise misleading claims and build progress on an explainer or simulation. For larger projects, finish a discrete milestone such as the storyboard, animatic, first usable simulation or learner integration, and record the next concrete step. Continue independent work when a render, provider or review is blocked.

## Produce and verify

- **Animated explainers.** Write a focused narration and storyboard tied to one learner outcome. Reuse the existing browser motion-graphics and FFmpeg pipeline for timing, charts and abstract processes. Use Blender for realistic scenes where spatial layout, physical objects, camera movement or a workplace action helps explain the lesson. Keep editable scene sources or a reproducible Blender Python build, and use a small animatic and key frames to check the composition before the full render. Check the complete clip, captions, transcript, audio balance, motion and timing. Store full renders through the existing media workflow and verify a learner can play the delivery copy from the lesson.
- **B-roll.** Review the storyboard for inserts that establish a setting, illustrate an action or cover an edit. Add each useful shot to the backlog with the information listed there. Use an available authorised Gemini video route for queued shots. If it is unavailable, mark the shot `needs Greg` and put its ID, generation prompt and return filename in the next user report. Continue editing with an existing shot or a placeholder. Check returned clips for continuity, visual artefacts, usable duration and rights. Record the source and any trim, audio removal or other edit before integration.
- **HTML simulations.** Embed a runnable HTML/CSS/JavaScript exercise in the relevant lesson, with instructions, realistic synthetic scenario data, consequences, a debrief and a retry path. Keep scenario data editable. Test the learner path at desktop and mobile widths with keyboard navigation and test the public build. Use browser `LanguageModel` or Web Speech APIs when they improve practice, such as spoken discovery calls or feedback on a handoff. Check [Prompt API](https://developer.chrome.com/docs/ai/prompt-api) and [Web Speech API](https://developer.mozilla.org/en-US/docs/Web/API/Web_Speech_API/Using_the_Web_Speech_API) support when implementing. Keep typing, scripted responses and meaningful rubric feedback usable on unsupported browsers or when learners decline microphone access. Request permission only when a learner invokes speech, explain where their input is processed, and keep any service credential outside browser code. Use deterministic rules for assessed scores.
- **Slide images.** Follow the [protected review instructions](cloud-task.md) and [geometry gates](../docs/image-review-quality-gates.md) for candidate or source rework. Fetch the current checksummed protected snapshot before selecting image work. If that fetch fails, continue the independent audit, film and simulation work. Use the server receipt to confirm candidate registration. Preserve reviewer decisions and `delivery-pending` items.

Validate the affected course source and generated delivery. Verify links, playback or exercise behaviour in a browser and confirm what shipped in the real learning surface. Commit and push verified work with the repository's attribution. When a site change triggers CI, confirm deployment and smoke-test the affected live lesson. Record coverage, completed backlog IDs, evidence, open dependencies and any B-roll request in the run report. If a run only updates planning documents, report that scope.

## Cloud setup and scheduling

1. In Codex Cloud, publish a course environment that can fetch the current Professional Practice `main`. The existing `document-handling` configuration has a historical checkout. A dedicated course environment lets us test dependencies and permissions separately from its other repositories. Prepare the Linux tools from [`cloud-setup.sh`](cloud-setup.sh) and add a headless Blender executable with a verified CPU render path. The two existing explainers also use Node, Playwright/Chromium and FFmpeg. Use the existing scoped AWS identity for the private review exchange and the appropriate media bucket permissions.
2. Start a fresh hosted run using GPT-6.2 Sol. Verify fetch and GitHub write access, course validation, a small Blender render, browser playback and a fresh protected S3 fetch. The exchange uses the Python SDK from `cloud-requirements.txt`. Confirm access to the actual bucket from the task. For media production, also verify the required upload and readback paths. Test optional narration and Gemini access before assigning those jobs to a run. Keep provider and AWS credentials in the environment's configured connections or vault.
3. If available in the workspace, ask a scheduled Dot task to start a new Codex Cloud task in the published course environment every Monday at 9 am Australia/Sydney. Ask it to select GPT-6.2 Sol, follow this file from current `main`, and report results and Gemini handoffs in ChatGPT. Confirm that the first triggered task ran in the named Cloud environment and that the actual task used the requested model. Verify the scheduler in **Scheduled** and the hosted task in Codex. The desktop automation is paused.
